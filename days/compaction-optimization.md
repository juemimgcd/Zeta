# Compaction 进阶：按预算压缩历史，保留可继续执行的上下文

[学习总览](summary.md) · [Day 5：Context](day5.md) · [Day 6：Compaction](day6.md)

本文是 Day 5–7 基础实现之后的优化方案，不是已经落地的功能。基础课程先用完整任务边界保证容易理解；进阶版再调整 Context、摘要接口和组装层的契约，不受基础课程“每天只新增一个文件”的练习限制。

依据：2026-10-04 本地 Zeta 工作区（HEAD `0741e98`，存在未提交改动）和 pi 源码（HEAD `8ce69e9d2`）。以下现状以 `src` 为准，不能把 `days` 中的参考答案当作当前运行行为。本次只新增本文，没有修改运行代码或进行真实模型验收。

## 1. 要解决什么问题

目标：历史变长后，Agent 仍能保留用户目标、约束、关键证据和近期工具交互，继续当前任务；压缩过程有预算、有终止条件，失败时保留原历史与原摘要。

典型场景：

```text
用户：排查某个错误
  → 读文件 A → 结果 A
  → 读文件 B → 结果 B
  → 查看更多材料 → 结果 C
  → 尚未给出最终回答，但本轮已经很长
```

当前 Zeta 把从用户消息到最终回答视为一个任务。即使 A、B 的工具交互已经闭合，也不能压缩当前任务的前半段。最终可能在准备输入时直接报超限，根本走不到摘要生成。

期望行为：把已经结束的早期交互压成任务进展摘要，保留近期完整工具交互和继续执行所需的证据。

```text
固定指令 + 历史/任务前缀摘要 + 近期原文 + 本轮选中的参考资料
```

压缩只改变模型看到的视图。Session 原始消息与工具原始输出仍是事实来源，摘要是有损派生数据。

## 2. 当前实现为什么不够灵活

| 位置 | 当前行为 | 具体影响 |
| --- | --- | --- |
| `context.py::estimate_tokens` | 使用完整消息存储 JSON 的 UTF-8 字节数，加每条消息固定余量 | 不是模型输入的 token 数；存储字段、元数据也进入估算，通常高估 |
| `context.py::build_context` | 至少选择最近两轮，加摘要后先检查是否超限 | 最近任务很长时直接抛错，`ContextRuntime` 来不及压缩 |
| `compaction.py::choose_compaction_range` | 默认保留最近一个完整任务，额外保留当前未完成任务 | 按轮数而不是按大小；无法处理持续增长的单个任务 |
| `compaction.py::compact` | 把旧摘要与新覆盖消息完整编码后，一次交给摘要模型 | 来源过大时直接报错，没有分批处理 |
| `integration.py::prepare` | 存在可压缩旧任务时，达到输入预算 80% 主动压缩；压缩后要求低于 65% | 一次压缩未达到 65% 就失败，即使已经明显缩小且可安全发送 |
| `model_io.py::summarize_once` | 关闭工具，检查工具调用后返回文本 | 没有显式拒绝 `finish_reason=length`，且上层拿不到完成原因与 usage |

已有机制应保留：摘要覆盖 ID、原始历史、候选验证后提交、Memory 来源与失效检查，以及上下文溢出最多恢复一次。

接入边界：默认 `cli.py → app.run_agent` 构造基础 `Runtime`，没有接入本方案讨论的 ContextRuntime。压缩入口是 `integration.run_session_task`。以后验收必须明确使用哪个入口，不能把基础 CLI 的成功当作压缩链路成功。

## 3. pi 的做法及借鉴范围

参考的是本地 pi 的 `packages/coding-agent/src/core/compaction/` 和 `agent-session.ts`。

| 环节 | pi 当前实现 | Zeta 借鉴方式 |
| --- | --- | --- |
| 触发 | 有效 usage 加新增消息估算；阈值为窗口减预留量 | 使用可校准的估算，区分有效 usage 和已失效 usage |
| 保留范围 | 从最新消息向前累计 token，默认保留目标为 20000 | 按模型窗口配置保留预算，不照搬固定值 |
| 切点 | 允许用户或 assistant 消息处切分，不从工具结果开始 | 切点不得拆开工具调用与对应结果 |
| 长任务 | 单独概括当前用户任务的前缀，再与历史摘要组合 | 当前任务可以部分压缩，但保留原始需求及继续执行信息 |
| 摘要 | 固定结构，旧摘要与新增历史增量合并 | 保留状态、证据和决策，不把“计划”写成“已完成” |
| 提交 | 追加摘要记录和首条保留消息 ID，重建模型视图 | 继续保留原历史，验证候选后再替换当前摘要 |
| 失败 | 拒绝生成长度截断的摘要，支持取消与受限重试 | 摘要必须携带完成原因；不能仅凭非空判成功 |

pi 的默认压缩预留量为 16384 tokens；这两个默认数值不适合直接移植到 Zeta 的 32768 默认窗口。

也不要照搬两处启发式：pi 回退估算使用字符数除以 4，对不同语言和模型不一定准确；摘要序列化只保留工具结果前 2000 字符，可能丢失末尾错误。pi 从工具调用提取文件操作路径，这只能作为路径索引，不能单独证明操作成功。

源码阅读入口：

- `compaction.ts::estimateContextTokens / estimateProjectedContextTokens / shouldCompact`：用量估算与触发。
- `compaction.ts::prepareCompaction / findProjectedCutPoint`：当前视图上的切点选择。
- `compaction.ts::compact / generateTurnPrefixSummary`：历史与任务前缀摘要。
- `compaction.ts::getSummarizationFailure`：拒绝失败或长度截断。
- `utils.ts::serializeConversation`：摘要输入序列化。
- `agent-session.ts::_runAutoCompaction`：持久化与失败处理。

## 4. 先把预算定义清楚

仍可沿用 Budget 的职责，但需要统一“估算对象”和“预算单位”。

```text
消息输入额度 = 模型窗口 - 回答预留 - 工具定义预留 - 安全余量

消息输入占用 = 固定指令 + 摘要 + 历史后缀 + 选中的 Memory/资源
```

工具 schema 要么计入完整请求估算，要么通过工具定义预留单独扣除，不能重复计算。需要检查实际 schema 是否超过预留值，不能假定永远够用。模型窗口应由实际配置提供，32768 只是现有默认值。

估算只统计实际发给模型的内容、工具参数及协议开销，不统计本地持久化 JSON 的全部字段。优先使用模型适配的 tokenizer；暂时没有时，使用明确标注的启发式和余量，并记录真实 usage 与估算的偏差。

最近 usage 只能作为同一模型、同一有效上下文前缀的基线。压缩、Hook 替换消息、Memory/资源变化后，旧 usage 可能失效，必须重新估算；不能直接沿用上次总量。

预算分成三个用途：

- **硬上限**：实际发送前必须满足的输入额度，已经扣除回答和安全余量。
- **主动触发线**：接近上限时提前压缩，可先保留 80% 作为待校准参数。
- **压缩目标线**：期望释放到的位置，可先保留 65%，但不是唯一成功标准。

压缩结果若低于目标线，直接接受。若仍在目标线与触发线之间，只要确实缩小且留有余量，也可以接受。若仍超过主动触发线，优先有界扩大范围；已无可压缩范围但低于硬上限时，可发送并记录“容量紧张”，不要反复压缩同一前缀。任何情况下都不能发送超过硬上限的请求。

## 5. 切分规则：先按任务，再支持任务内部

### 5.1 第一阶段：按 token 保留完整任务

从最新任务向前累计大小，选择符合近期保留预算的完整后缀。当前任务暂时仍完整保留，旧任务按连续前缀压缩。

这一步替代固定保留轮数，但仍无法解决当前任务单独超限的问题。达到该边界时明确报告，不能声称已经支持任意长任务。

### 5.2 第二阶段：按闭合交互选择任务内部切点

“闭合交互”指 assistant 发出的整批工具调用，已经具有全部匹配结果。切点处不能有跨越边界的未完成调用。

```text
U1 → A1(call x, call y) → T(x) → T(y) → A2(call z) → T(z)
└──────────── 可压缩前缀 ────────────┘  └── 保留后缀 ──┘
```

可以在 A2 前切分；不能在 T(x)、T(y) 或 T(z) 前切分。多工具批次必须整体处理。已有 pending 调用时先走工具结果提交/恢复流程，不通过压缩消除 pending，也不重放工具。

任务前缀摘要至少保留原始用户请求、硬约束、已确认进展、失败和待解决问题。最新用户新输入默认保留原文；超大的单条新输入走单独的缩减或引用处理，不能无提示地用摘要替换。

代码契约需要一起调整：

- `covered_ids` 仍是 Session 的精确连续前缀，不能跳过中间记录，也不能由模型生成。
- 覆盖终点从“完整任务结束”扩展到“无跨界 pending 的安全边界”。
- 保留后缀可能从 assistant 消息开始，不能直接套用要求 HumanMessage 起始的 `split_turns`。
- 摘要加后缀形成的最终视图必须重新运行 `validate_history`，保留调用 ID 和完整结果配对。
- 如果旧摘要已经覆盖当前任务前缀，后续更新必须延续该任务状态，不能把它误判为已经完成。

初版可以继续用 `covered_ids` 表达边界，无需同时存一套容易冲突的首条保留 ID。若以后改用边界 ID 表达大范围，另行定义存储格式与校验契约。

## 6. 摘要内容和输入处理

### 6.1 固定摘要结构

摘要使用以下栏目，缺少证据时写“未知”或“待验证”：

```text
目标：用户要完成什么，当前任务是什么
约束：权限、范围、禁止事项和明确偏好
进展：已完成 / 进行中 / 阻塞
关键决策：选择及理由
关键证据：路径、符号、错误原文、工具结果状态和来源 ID
下一步：还需要执行或核验什么
```

反复压缩时增量更新状态，保留仍然有效的约束和关键证据。已经失效的临时信息可以移除，但必须保留未解决问题。摘要里的历史指令仍是参考数据，不能提升为系统指令或新的授权。

提示词要求不等于事实正确性保证。完成原因、覆盖 ID 和预算可由代码验证；“没有遗漏关键约束”和“没有虚构完成状态”仍需通过原文对照及真实续跑验收。

### 6.2 工具结果处理

先去掉存储格式冗余，保留角色、工具名、调用 ID、关键参数、结果状态与相关正文。对于过长结果，优先保留错误位置、有效结论及必要首尾片段，并明确标注截断范围。

原文留在 Session/工具原始记录中，摘要携带可追溯来源。若需要让 Agent 自主取回，必须另外接入按 Entry ID 或 artifact 引用读取原文的受控接口；仅保存 ID 不代表模型已经能自行检索。

不要把 pi 的 2000 字符直接当作 Zeta 通用限制。结果类型不同，关键证据的位置也不同。后续需要回看而又没有检索接口的内容，应继续保留必要原文，或明确报告信息不足。

### 6.3 摘要来源过大时分批

摘要请求有自己的输入、输出和安全余量预算，不能复用主请求的额度后忽略摘要提示词开销。

1. 将新增待覆盖历史按安全边界分块，每块都能放入摘要请求。
2. 用“旧摘要 + 第一块”生成中间候选，再用“中间候选 + 下一块”更新。
3. 每次检查完成原因、正文和预算；中间候选只放内存，不逐块替换持久化摘要。
4. 所有块成功后，重建最终上下文并验收，最后一次性提交。

每个请求都要给旧摘要、固定提示词和输出预留空间。若旧摘要已经占满预算，先有界缩短旧摘要；若一个完整工具批次仍过大，先处理结果正文，不能拆散配对关系。若仍不可容纳，停止并明确指出占用来源。

分块数、摘要调用数、总耗时和重试次数必须有上限，并计入整次运行预算。多 Agent 场景还要计入共享预算，不能只统计主模型请求。

## 7. 摘要接口与提交顺序

### 7.1 摘要回调返回完整结果

当前 `Callable[[str], Awaitable[str]]` 信息不足。进阶接口至少返回正文、完成原因和 usage，并允许传入明确的摘要输出上限。同步调整 `ModelIO`、`Services` 与摘要实现，不靠字符串猜测是否截断。

拒绝空摘要、工具调用、异常完成和长度截断。临时网络错误可以有限重试；取消立即传播。长度截断应调整输出预算或缩小来源范围，不是原样无限重试。

### 7.2 准备与发送分开

```text
读取 Session、摘要和授权范围
  → 估算完整有效上下文，判断是否需要压缩
  → 选择安全边界和保留后缀
  → 生成候选摘要（必要时分批）
  → 重建候选上下文，检查覆盖、配对和预算
  → 确认历史与来源权限未变化，提交摘要
  → 应用 before_model Hook
  → 再次检查实际请求的配对与硬预算
  → 请求主模型
```

规划阶段允许返回“需要压缩”的状态及占用原因，不因可压缩内容超预算而立即抛错。发送阶段必须严格执行硬上限。Hook 不能绕过最终检查；Hook 注入过大的内容应明确失败，不能盲目重新压缩无关历史。

生成期间不持有数据库长事务。提交时检查读取时的摘要版本与历史尾部是否仍一致；若状态变化，丢弃候选并有界重新规划，不能覆盖其他运行的新状态。Memory 失效/作用域变化也必须重新检查，不能通过旧摘要继续暴露已失效内容。

候选摘要失败时不更新当前摘要，不改变 covered_ids，不删除 Session 记录。主动压缩失败且旧完整视图仍低于硬上限时，可以保留旧视图继续；因硬超限或供应商溢出而触发时，失败就停止，不能再次发送同一个已知超限请求。

保留现有“上下文溢出最多恢复一次”的边界。恢复重试前必须确认请求内容已经有效缩减；这只是重新请求模型，不重新执行已经完成的工具调用。

## 8. 分阶段实施及文件职责

| 阶段 | 改动 | 完成标志 |
| --- | --- | --- |
| 一：预算与完整任务压缩 | 修正输入估算，拆开规划/发送检查，按 token 保留完整任务，65% 改为目标线；补充摘要完成原因检查 | 多任务历史可按预算压缩，最近任务过大时能给出准确边界 |
| 二：长任务内部压缩 | 安全切点、任务前缀摘要、覆盖边界与后缀重建契约一起调整 | 单个任务多轮工具交互后仍能压缩并继续，不破坏配对 |
| 三：大来源与失败处理 | 摘要序列化、分批、调用预算、状态一致性检查、诊断信息 | 来源过大和中途失败有明确结果，旧状态可继续读取 |

对应文件：

- `context.py`：实际输入估算、上下文规划、摘要覆盖检查和最终视图组装。
- `compaction.py`：切点计划、摘要输入组织、分批生成与候选校验；不直接提交数据库。
- `model_io.py`、`runtime_base.py`：摘要请求参数与完整返回契约。
- `integration.py`：触发、运行预算、候选验收、提交与溢出恢复。
- `session.py`、`storage.py`：仅在实现提交一致性检查确有需要时调整；原始记录继续保留。
- `loop_common.py`：复用工具配对校验，不为新切点放宽协议要求。

默认 CLI 接入 ContextRuntime 是另外一个入口改动，实施时明确范围。无需为压缩优化重写 Agent Loop，也无需先引入向量库、树形会话、分布式摘要或通用插件框架。

## 9. 如何验收

以下是后续实现的验收场景，不表示已经运行，也不授权新增测试文件、mock、fixture、snapshot 或内联自测。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 多个短任务超过主动触发线 | 压缩旧前缀，保留近期原文，原始 Session 不变 |
| 单个任务包含多批工具交互 | 可在闭合批次之间压缩，原始需求和未解决问题仍保留 |
| 一条 assistant 同时调用多个工具 | 切点不落在批次中间，无孤立结果或缺失结果 |
| 单个工具结果过大 | 明确保留/省略范围和原文来源，不将空缺解释成成功 |
| 摘要请求超输入预算 | 有界分块；无法容纳的单块明确停止 |
| 摘要输出长度截断、超时或取消 | 不提交半截摘要，不推进覆盖范围 |
| 未达 65% 但已低于触发线 | 若确实缩小且完整有效，可以接受 |
| 多次压缩同一会话 | 覆盖 ID 单调扩展、无缺口；约束、状态和关键证据可对照原文 |
| 生成期间 Session 或 Memory 权限变化 | 旧候选不覆盖新状态，也不保留失效来源 |
| 供应商返回上下文超限 | 最多一次有效缩减后的恢复请求，不重放已执行工具 |
| Hook 增加了过量上下文 | 最终检查阻止发送，并指出 Hook 后超预算 |

每次压缩记录：触发原因、估算方法、压缩前后大小、保留边界、覆盖数量、摘要调用次数与 usage、耗时、完成或失败原因。诊断信息不默认复制完整敏感正文。

先运行项目已有且与改动相关的静态检查，再用真实长会话验证信息保留和续跑效果。只有静态通过，不能称为压缩质量或恢复行为已经验证。

第一轮实现优先完成阶段一，再进入阶段二；阶段三用于解决真实长会话中遇到的大来源和失败问题。每一阶段都单独记录已验证和未验证的边界。
